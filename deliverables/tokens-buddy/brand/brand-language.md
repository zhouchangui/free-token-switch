- 短介绍: TokensBuddy 是一款面向 AI 编码用户、独立开发者和小团队的桌面工具。它以 cc-switch 式的多工具 Token / Provider 切换为基础，连接 Claude、Codex、Gemini、OpenCode、OpenClaw、Hermes 等 AI 编码入口，并在此之上加入好友分享、市场发布与 Token 交易能力。它的核心不是单纯管理配置，而是让 AI Token 从“只供自己切换使用”进一步变成“可以分享、可以交易、可以重新流动的开发资源”。

## 产品核心重构

### 用户更正

用户明确指出: 这个产品的核心就是在 cc-switch 的基础上面增加了 Token 分享和交易。

### 更新后的产品判断

- cc-switch 解决第一层问题: 我有多个 AI 工具、多个 Provider、多个 Token，怎么快速切换和使用。
- TokensBuddy 解决第二层问题: 当这些 Token 可以被稳定接入后，怎么把闲置或可用 Token 分享给好友，或者发布到市场进行交易。
- 因此品牌不应只讲“工具链中控”，也不应只讲“闲置变现”。更准确的主轴是:
  - 切换是基础能力。
  - 分享和交易是新增价值。
  - 流动是品牌故事。

### 修正后的目标用户

| 优先级 | 目标用户 | 既有行为 | TokensBuddy 带来的新增价值 |
| --- | --- | --- | --- |
| P0 | cc-switch 既有用户 / 多 Provider 切换用户 | 已经在多个 AI 编码工具和 Provider 之间切换 Token | 在切换之外，把可用 Token 分享给好友或进入市场交易 |
| P0 | 有闲置 Token 的 AI 开发者 | 自己用不完，或者多个账号/套餐里有剩余额度 | 不只是放着浪费，而是通过分享或交易重新流动 |
| P1 | 需要临时 Token 的开发者或好友 | 临时缺额度、缺可用 Provider，不想手动配一堆 Key | 通过分享链接或市场更快接入可用 Token |
| P1 | 小团队/协作场景 | 需要把某个 Provider 临时给同伴使用 | 不直接裸发 Key，而是通过可控通道分享 |
| P2 | 价格敏感的 AI 编码用户 | 在不同供应商、套餐和市场之间找性价比 | 可以发现和交易更合适的 Token 资源 |

### 更新后的品牌承诺

TokensBuddy 不是把 cc-switch 换个名字，而是把“Token 切换器”升级成“Token 流通工具”: 先让用户能顺手切换和使用自己的 Token，再让用不完的 Token 可以被分享、被交易、被真正用起来。

## 核心优先的文案候选

### 主标语

0. 让闲置的 Token 流动起来
   - 状态: 用户选择
   - 适合: 直接抓住 TokensBuddy 相对 cc-switch 的新增价值，把“闲置”“分享”“交易”“流动”压缩进一句话。
   - 风险: 对 cc-switch 的切换基础表达较弱，需要能力句补充。
1. 不止切换 Token，也让 Token 流动起来
   - 适合: 最准确地承接 cc-switch 底座和新增分享/交易价值。
   - 风险: 稍长，但表达完整。
2. 从 Token 切换，到 Token 流通
   - 适合: 品牌升级叙事，简洁、有阶段感。
   - 风险: “流通”略抽象，需要能力句补足“分享和交易”。
3. 让闲置 Token 找到需要它的人
   - 适合: 强打供需匹配和市场价值，用户更容易懂。
   - 风险: 弱化了 cc-switch 的基础能力。
4. 切换、分享、交易你的 AI Token
   - 适合: 直给型功能标语，适合 README 和下载页。
   - 风险: 比较工具化，品牌感弱。
5. 你的 AI Token 搭子: 能切换，也能流通
   - 适合: 中文社区传播，保留“搭子”亲近感。
   - 风险: 不适合英文主场景。
6. 把用不完的 Token，交给需要的人
   - 适合: 好友分享和市场交易情绪钩子。
   - 风险: 对 Provider 管理和切换能力表达不足。

### 能力句

1. 面向 AI 编码工具的 Token 切换、分享与交易工作台。
   - 适合: 当前最平衡，直接点出三件事。
2. 在 cc-switch 的多工具 Provider 切换基础上，增加好友分享、市场发布与 Token 交易。
   - 适合: 面向熟悉 cc-switch 的老用户，升级路径清楚。
3. 统一管理 AI Provider，并把闲置 Token 变成可分享、可交易的资源。
   - 适合: 同时讲管理和流动价值。
4. 从本地切换到公网分享，从好友使用到市场交易，管理 Token 的完整流转。
   - 适合: 功能页和产品介绍，流程感强。
5. 连接 Claude、Codex、Gemini、OpenCode、OpenClaw 与 Hermes 的 Token 使用、分享和交易。
   - 适合: 开发者识别度强，明确支持范围。
6. 一个让 AI Token 能切换、能分享、能交易的桌面工具。
   - 适合: 最通俗，适合首页短介绍。

### 核心叙事

1. 从切换器到流通工具
   - 叙事: cc-switch 让开发者能在不同 AI 工具和 Provider 之间切换 Token；TokensBuddy 在此基础上继续往前走，让 Token 不只服务自己，也能分享给好友，或进入市场交易给需要的人。
   - 适合: 品牌升级、官网首屏、README。
2. 让闲置 Token 回到真实开发里
   - 叙事: 很多 AI Token 被买下、配置好，却常常只在某个账号或某台机器里闲置。TokensBuddy 先让它们可以被顺手切换，再让它们通过分享和交易重新进入真实开发场景。
   - 适合: 市场、交易、商业化叙事。
3. 先管好，再流动
   - 叙事: Token 分享和交易的前提是管理清楚。TokensBuddy 保留 cc-switch 的本地切换和 Provider 管理能力，再把分享通道、市场发布和交易结算接上，让流动建立在可控之上。
   - 适合: 安全感、信任感、产品架构解释。
4. 从个人配置到 Token 网络
   - 叙事: Token 过去只是个人配置文件里的一个 Key；TokensBuddy 把它变成可切换、可分享、可交易的网络资源，让供给方和需求方更容易连接。
   - 适合: 长期品牌愿景。
5. 给 AI 编码用户一个 Token 搭子
   - 叙事: 你可以用它切换自己的 Token，也可以把用不完的额度交给搭子，或者从别人那里找到可用资源。TokensBuddy 让 Token 不再只是孤立的 Key，而是能和人协作的开发资源。
   - 适合: 中文社区和社媒传播。

## 受众优先重构

### 修正说明

前一版候选更多是在描述“产品有什么能力”，目标用户视角不足。随后又根据用户反馈进一步修正: 产品核心不是泛泛的 AI 工具链中控，而是在 cc-switch 的切换基础上增加 Token 分享和交易。新的文案原则是:

- 先回答“谁会打开 TokensBuddy”。
- 再回答“他为什么现在需要它”。
- 最后明确“分享和交易才是 TokensBuddy 相对 cc-switch 的新增价值”。

### 目标用户矩阵

| 优先级 | 目标用户 | 用户心里在想什么 | 主要焦虑 | 品牌应该承诺什么 |
| --- | --- | --- | --- | --- |
| P0 | AI 编码工具重度用户 | 我每天在 Claude、Codex、Gemini、OpenCode、OpenClaw、Hermes 之间切换 | 配置散、额度乱、工具突然不可用 | 把多工具 Token 使用变清楚、稳定、可控 |
| P0 | 多 Provider 管理者 | 我有官方、第三方、中转、OAuth、不同 Base URL | 不知道哪个还能用、哪个更划算、怎么切回去 | 统一管理 Provider、额度、路由和健康状态 |
| P1 | 小团队或好友协作用户 | 我想把可用额度给可信的人临时用 | 怕泄露、怕失控、怕不知道怎么停止 | 分享前可确认，分享后可控制、可停止 |
| P1 | 闲置额度拥有者 | 我有用不完的额度，想让它有价值 | 怕被误解成倒卖，怕收款和权限不可信 | 在明确边界里释放剩余价值 |
| P2 | 低成本 Token 寻找者 | 我临时需要可用额度，不想到处找 | 怕不可用、怕不透明、怕配置麻烦 | 找到可用资源，并快速接入工具 |
| P2 | AI 工具体系玩家 | 我还管 Skills、MCP、OpenClaw Workspace、Hermes Memory | 上下文资产散，工具链越来越碎 | 做 AI 开发工具链的本地中控 |

### 定位含义

- 首要用户建议锁定: AI 编码工具重度用户 + 多 Provider 管理者。
- 次要用户建议承接: 小团队/好友协作用户 + 闲置额度拥有者。
- 暂不建议把低成本购买者作为主入口，否则品牌会更像市场或交易平台。
- “变现”适合放进能力句或二级介绍，不建议成为主标语的第一钩子。

## 受众导向文案候选

### 路线 A: AI 编码重度用户优先

- 目标用户: 每天同时使用 Claude、Codex、Gemini、OpenCode、OpenClaw、Hermes 的开发者。
- 用户洞察: 他们最痛的不是“闲置额度能不能赚钱”，而是“我的 AI 编码工具今天能不能稳定、清楚、便宜地跑起来”。
- 主标语:
  1. 让 AI 编码工具用上对的 Token
  2. 管好每一个 AI 编码入口
  3. 别再为 AI 工具手改 Token
- 能力句:
  1. 统一管理 Claude、Codex、Gemini、OpenCode、OpenClaw 与 Hermes 的 Provider、额度和路由。
  2. 一个面向 AI 编码工具的 Token、Provider 与本地代理工作台。
  3. 帮开发者看清额度、切换 Provider、控制路由，并在需要时分享可用资源。
- 核心叙事:
  - AI 编码用户已经不缺工具，缺的是一个能把工具背后的 Token、Provider、额度和路由管清楚的地方。TokensBuddy 让每个编码入口都能接上合适的资源，而不是让用户在配置文件、Web UI 和命令行之间来回救火。
- 最适合:
  - App 首页、README、GitHub、开发者社区。
- 风险:
  - 对“分享与变现”的差异化表达较弱，需要在二级文案补上。

### 路线 B: 多 Provider 管理者优先

- 目标用户: 有多个 API Key、Base URL、OAuth、官方/第三方/中转供应商的人。
- 用户洞察: 他们需要的不是漂亮的“市场故事”，而是状态可见、切换可靠、出问题能回退。
- 主标语:
  1. 把分散的 AI Provider 管清楚
  2. 你的 AI Token 控制台
  3. 每个 Provider，都有清楚状态
- 能力句:
  1. 统一管理 AI Provider、Token 额度、健康状态、本地路由和分享通道。
  2. 一个让 API Token 可见、可控、可回退的本地桌面工具。
  3. 从配置到用量，从切换到分享，把 AI Provider 管理收进一个工作台。
- 核心叙事:
  - 多 Provider 不是自由，混乱的多 Provider 才是负担。TokensBuddy 把分散的 Key、额度、路由和状态整理成清晰的控制台，让开发者知道现在该用哪个、为什么能用、出了问题怎么回来。
- 最适合:
  - 桌面 App 视觉系统、设置页、Provider 管理页、官网功能区。
- 风险:
  - 亲和力稍弱，需要用“Buddy/搭子”在微文案中补温度。

### 路线 C: 好友协作和可信分享优先

- 目标用户: 想把可用额度临时分享给朋友、小团队或协作者的人。
- 用户洞察: 他们愿意分享，但前提是知道分享了什么、给了谁、什么时候停止。
- 主标语:
  1. 把可用 AI 额度放心交给搭子
  2. 让 Token 分享更清楚、更可控
  3. 好友要用 AI 额度，不必再手动发 Key
- 能力句:
  1. 为 AI 开发者提供可确认、可停止、可回退的 Token 分享与接入工作台。
  2. 把本地 Provider 变成受控分享通道，让朋友和团队更快接入可用 AI 资源。
  3. 管理自己的 Token，也安全地分享给可信的人。
- 核心叙事:
  - 直接发 Key 太危险，临时协作又太常见。TokensBuddy 把“分享 Token”变成一个可确认、可见、可停止的通道，让朋友能用上资源，而你仍然掌握边界。
- 最适合:
  - 好友分享功能、中文社区传播、短教程。
- 风险:
  - 若作为主品牌，会缩小产品的工具平台感。

### 路线 D: 闲置额度价值释放优先

- 目标用户: 有闲置 API 额度，并愿意在平台规则内分享或变现的人。
- 用户洞察: 他们不是只想赚钱，也担心安全、合规、收款和被误解。
- 主标语:
  1. 让闲置 AI 额度有清楚去处
  2. 管好额度，也释放剩余价值
  3. 让用不完的 Token 回到开发里
- 能力句:
  1. 一个帮助 AI 开发者管理、分享并释放闲置 Token 价值的本地工作台。
  2. 从自用管理到可信分享，再到市场发布，让闲置 API 额度被看见、被控制、被利用。
  3. 把暂时用不完的 AI API 资源，变成可管理、可分享、可结算的开发能力。
- 核心叙事:
  - 闲置额度不是浪费，也不该变成失控风险。TokensBuddy 先帮用户管好自己的 Token，再在明确权限、通道和收款边界里，让剩余价值重新进入开发协作。
- 最适合:
  - 市场页、卖家入口、商业化介绍。
- 风险:
  - 如果放在品牌第一层，容易把 TokensBuddy 误读成交易平台。

### 路线 E: AI 工具链中控优先

- 目标用户: 同时管理 Provider、Skills、MCP、OpenClaw Workspace、Hermes Memory 等上下文资产的高级用户。
- 用户洞察: AI 编码时代的问题不是单个工具不好用，而是工具链上下文越来越碎。
- 主标语:
  1. 你的 AI 开发工具链中控台
  2. 把 AI 编码上下文收进一个工作台
  3. 从 Token 到工具链，一处管理
- 能力句:
  1. 统一管理 AI 编码工具的 Provider、Token、Skills、MCP、Workspace 与 Memory。
  2. 面向高级 AI 开发者的本地控制台，连接 Token、工具、上下文和协作资源。
  3. 让分散在各个 AI 工具里的配置和上下文资产变得可见、可控、可迁移。
- 核心叙事:
  - AI 编码工作正在从“一个模型”变成“一整套工具链”。TokensBuddy 负责把底层 Token、Provider、代理和上下文资产连接起来，让高级用户拥有一个稳定的本地中控。
- 最适合:
  - 长期产品定位、未来版本、面向 OpenClaw/Hermes 用户的叙事。
- 风险:
  - 当前认知门槛更高，不适合做最短主标语。

## 受众与场景

- 首要受众:
  - 同时使用 Claude Code、Codex、Gemini CLI、OpenCode、OpenClaw、Hermes 等工具的 AI 编码用户。
  - 需要管理多个 Provider、API Key、Base URL、OAuth、余额、用量和代理路由的独立开发者或小团队。
  - 拥有闲置 API 额度，希望在可信边界内分享给朋友或参与市场变现的用户。
  - 需要本地可控、配置透明、能回退到官方配置的高级工具用户。
- 主要场景:
  - 在多个 AI 编码工具之间快速切换可用 Provider。
  - 查询额度、用量、余额和供应商健康状态。
  - 启动本地代理、配置路由、处理故障转移。
  - 把当前供应商配置打包为好友分享通道。
  - 将可用 Token 额度发布到 tokensbuddy.com 或 Clawtip 相关市场流程。
  - 管理 Skills、MCP、OpenClaw Workspace、Hermes Memory 等开发者上下文资产。
- 用户痛点:
  - AI 工具和 Provider 配置散落在不同文件、目录和 Web UI 中。
  - 额度状态不透明，容易不知道哪个 Key 还能用、哪个更划算。
  - 切换工具和供应商成本高，出错后回滚麻烦。
  - 闲置额度缺少可信、低摩擦、可控的分享方式。
  - “卖 Token”容易让用户担心安全、隐私、规则和收款可信度。
- 希望形成的感知:
  - 专业、可信、透明、可控。
  - 懂 AI 开发者的日常工作流。
  - 有一点“搭子”的亲近感，但不是玩具化或娱乐化产品。
  - 像一个安静可靠的控制台，而不是浮夸的交易所。

## 专家评估摘要

- Brand Guardian:
  - 推荐把品牌主轴定为“可信的开发者 Token 工作台”，而不是单纯“卖 Token”。这样能保护长期品牌价值，也能降低市场分享功能带来的合规和信任压力。
  - “TokensBuddy + Token 搭子”可以共存: 英文名保持国际化和 GitHub 识别度，中文辅助名负责社区亲和力。
- UX Researcher:
  - 用户真正需要的是可控、可回退和低风险操作感。视觉和文案应突出配置状态、额度可见性、通道确认、分享边界，而不是只讲省钱或赚钱。
  - 新用户可能先被“多工具管理”吸引，熟悉后才使用“分享与变现”。首屏信息层级建议先工具可信，再流动价值。
- Visual Storyteller:
  - 最强叙事是“从孤岛到流动”: 分散的 Token、Provider 和工具配置被整理成一条可见、可控的资源流。
  - 后续视觉方向可以围绕“连接节点、路由流线、可视化额度、可信通道”展开，而不是围绕钱币或交易图表。
- Whimsy Injector:
  - “Buddy/搭子”的趣味应出现在微文案、空状态、成功反馈、轻量插图或 icon 细节里，不应压过核心控制台体验。
  - 可以保留一点温暖的陪伴感，例如“准备分享通道”“这个 Provider 现在很健康”，但避免拟人化过度。
