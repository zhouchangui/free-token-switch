## 产品前提

- 推断的产品类别: 面向 AI 编码用户的本地桌面工作台。
- 这个产品是什么:
  - 一个管理 Claude、Codex、Gemini、OpenCode、OpenClaw、Hermes 等 AI 编码工具 Provider / Token 的桌面应用。
  - 在多工具切换和本地代理基础上，提供好友分享、市场发布、交易/结算相关能力。
  - 它把“闲置 Token”从个人配置文件里的孤立资源，变成可以被看见、测试、切换、分享和受控使用的开发资源。
- 这个产品不是什么:
  - 不是加密货币交易所、收益平台、钱包产品或投机工具。
  - 不是只卖 Token 的 marketplace。
  - 不是面向泛办公人群的轻量订阅管理工具。
  - 不是靠吉祥物或社交关系驱动的社区产品。
- 首要用户:
  - 同时使用多个 AI 编码工具、多个 Provider、多个 API Key / OAuth / Base URL 的开发者。
  - 有闲置或多余 AI Token，并希望在安全边界内分享或释放价值的开发者。
- 次要用户:
  - 小团队、好友协作场景中，需要临时共享可用 AI 资源的人。
  - 价格敏感、临时需要可用 Token 的 AI 编码用户。
- 用户问题:
  - Provider 配置分散，当前使用哪个、哪个可用、哪个成本合适不清楚。
  - 闲置 Token 放在账号或本机配置里，无法被需要的人顺手使用。
  - 直接发 Key 风险高，市场发布又需要状态、权限和结算边界。
- 用户动机:
  - 更稳定地让 AI 编码工具跑起来。
  - 少手改配置、少在多个工具之间救火。
  - 把用不完的 Token 分享给可信的人，或在规则内转化成价值。
- 信任障碍:
  - 担心 Token 泄露、滥用、不可停止。
  - 担心“交易/变现”看起来像灰色市场或投机产品。
  - 担心工具太复杂，不知道当前分享、代理、市场发布处于什么状态。
- 决策触发点:
  - 用户有多个 Provider，经常切换或排障。
  - 某个套餐/账号有剩余额度，自己短期用不完。
  - 好友或团队临时缺可用 Token。
  - 用户希望用可见状态和确认流程替代裸发 Key。
- 战略机会:
  - 用“专业桌面控制台”建立可信底座，再用“让闲置 Token 流动起来”讲清新增价值。
  - 在视觉上把流动解释为“可控使用”，而不是“交易赚钱”。
- 前提状态: 已确认

- 能力句: 面向 AI 编码工具的本地 Token 控制台，支持 Provider 切换、可控分享与市场交易。
- 一句话介绍: TokensBuddy 帮 AI 编码用户管理和切换多工具 Provider，并让用不完的 Token 在可信边界内分享、发布和重新被使用。
- 短介绍: TokensBuddy 是一款面向 AI 编码用户的桌面工作台。它统一管理 Claude、Codex、Gemini、OpenCode、OpenClaw、Hermes 等工具背后的 Provider、Token、路由和状态，并在本地可控的基础上提供好友分享与市场发布能力。它的重点不是制造交易感，而是让开发者看清资源、控制边界，并把闲置 Token 带回真实开发场景。

## 受众与场景

- 首要受众:
  - AI 编码工具重度用户。
  - 多 Provider / 多 Token 管理者。
  - 有闲置 Token 并愿意分享或发布的开发者。
- 次要受众:
  - 临时需要可用 Token 的好友、协作者、小团队成员。
  - 关注成本和可用性的 AI 编码用户。
- 主要场景:
  - 管理和切换不同 AI 工具的 Provider。
  - 查看用量、健康状态、当前路由和代理接管状态。
  - 启动好友分享通道。
  - 发布市场、创建订单、完成一次付费调用。
  - 通过 deeplink 或导入流程接入共享 Provider。
- 用户痛点:
  - 配置分散，信任成本高。
  - 分享和交易流程容易显得危险或不透明。
  - 市场能力如果视觉过强，会盖过桌面工具本体。
- 用户动机:
  - 少折腾配置，多把 AI 编码工具用起来。
  - 让剩余 Token 不浪费。
  - 在不裸发 Key 的前提下协作。
- 信任障碍:
  - Token 泄露、滥用、无法停止。
  - 市场发布像灰产或投机。
  - 桌面工具界面复杂，状态解释不足。
- 希望形成的感知:
  - 专业、清楚、可控。
  - 资源会流动，但每条流动都有边界。
  - 这是开发者工具，不是交易所。

## 受众导向备选方案

### 路线 A: 专业桌面控制台

- 目标用户: 多 AI 编码工具用户、多 Provider 管理者、有闲置 Token 的开发者。
- 主标语: 让闲置 Token 流动起来。
- 能力句: 面向 AI 编码工具的本地 Token 控制台，支持 Provider 切换、可控分享与市场交易。
- 核心叙事: 先看清 Token 和 Provider，再让闲置资源在可控边界内被使用。
- 取舍: 最适合 App 和长期信任；情绪记忆点需要通过局部流动图形和“搭子”微文案补足。
- 状态: 用户选择。

### 路线 B: 开发者资源网络

- 目标用户: 好友协作、小团队、共享资源供需双方。
- 主标语: 让闲置 Token 流动起来。
- 能力句: 把本地 Provider 变成可分享、可停止、可追踪的开发资源通道。
- 核心叙事: Token 不再是孤立 Key，而是能在可信关系和市场规则中被重新使用的资源。
- 取舍: 传播性更强，但如果作为主视觉容易偏社区化，弱化专业桌面工具感。
- 状态: 保留为次级参考，不作为第一眼方向。

### 路线 C: 轻量市场工具

- 目标用户: 发布闲置 Token 的卖家、临时购买可用资源的开发者。
- 主标语: 让闲置 Token 流动起来。
- 能力句: 从 Provider 测试到市场发布，再到订单调用，让闲置资源完成一次可见流转。
- 核心叙事: 把闲置资源发布给需要的人，并用价格、状态和订单确认建立规则。
- 取舍: 商业价值最直接，但风险是像交易平台或投机产品。
- 状态: 不作为主视觉，只允许进入市场页面子语言。

## 专家评估摘要

## Brand Guardian 评审

- 一致性判断: 主标语可以保留，但必须由“本地控制台”和“可信边界”承接，否则容易被误读为交易/变现产品。
- 差异化判断: “AI 编码工具 Token 控制台 + 可控分享/市场”比单纯 Provider manager 或 marketplace 更有差异。
- 风险: 视觉若偏交易所、钱包或霓虹科技，会削弱长期信任。
- 建议修改: 所有首屏、logo、icon 和 App UI 都先表达控制与状态，再表达流动。
- 是否建议进入下一阶段: 是。

## UX Researcher 评审

- 首要用户判断: 应优先服务每天打开工具切换 Provider 的开发者，而不是只服务卖家。
- 关键使用场景: Provider 管理、当前状态、分享通道、市场发布、订单调用。
- 信任障碍: Token 会不会泄露、分享能不能停、市场发布是否透明。
- 可能误解: “流动”可能被理解成金融流动性或 Token 倒卖。
- 建议修改: 视觉和文案都要把“可控、可见、可停止”放进产品层级。

## Visual Storyteller 评审

- 核心叙事: 闲置 Token 从孤立配置回到真实开发使用。
- 视觉隐喻: 本地控制台、资源节点、受控通道、状态灯、边界线。
- 传播记忆点: “让闲置 Token 流动起来”可以保留，但画面必须显示“被控制的流动”。
- 延展场景: App icon、官网首屏、README 图、分享成功页、市场发布流程。
- 风险与修改建议: 不要使用金币、收益曲线、交易大厅等隐喻。
